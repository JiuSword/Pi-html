Pi Agent 框架 速览

面向 Agent 开发工程师。基于 earendil-works/pi 源码、官方文档与完整 git 历史的提炼版，只回答三个问题：它是什么、值不值得用、有哪些坑。

01一句话结论

“There are many agent harnesses but this one is yours.”
—— pi.dev 官方 slogan

Pi 是一个刻意做减法的 Agent harness：内核极小、扩展点极多、上下文极省。它的定位不是「多 Agent 编排平台」，而是可以被你改造成任何样子的底座。

30 秒版本 14 个 TypeScript 包、18 万行源码，但真正的 Agent 循环只有 949 行；复杂度全部花在「工具如何暴露给模型」「上下文如何回收」「能力如何插进来」这三个真问题上。 如果你要做可嵌入、可扩展、成本可控的编码/终端 Agent，它值得认真评估；如果你要开箱即用的 SaaS 或多 Agent 编排，它不是答案。

04五个关键设计（真正的价值所在）

这五条是自研 Agent 时最容易踩坑、也最值得直接抄的部分。

1. Transcript 是唯一权威

会话记录拥有 system prompt 与工具声明；SessionManager 拥有模型上下文。给 session.agent.state.messages 赋值不会改变持久化上下文——想注入历史必须构造带 entry 的 manager，或用 prepareRequest。这一条直接消灭「UI 看到的上下文 ≠ 模型看到的上下文」这类最难查的 bug。

packages/agent/README.md · docs/sdk.md

2. 工具的五级暴露模型

把「是否向模型声明」和「是否可被其它工具调用」拆成两个维度：direct（默认）/ model-only / codemode / deferred / hidden。MCP 时代工具数量爆炸时，这比「全量塞 schema」省下大量 token；配合 prepareLoadout()，编排型工具可以自己决定模型看到什么。

docs/extensions.md · src/core/extensions/types.ts

3. 事件驱动 + 三个明确的 turn 钩子

8 种事件顺序固定；每轮请求的生命周期是 prepareRequest → 模型 → 工具 → finishTurn → turn_end。beforeToolCall 可阻止调用、afterToolCall 可改写结果、finishTurn 决定续跑还是收尾。并行工具执行时事件按完成顺序、落盘按源码顺序——顺序语义被显式定义，不靠默契。

packages/agent/src/agent-loop.ts（949 行）

4. 生产级的上下文回收

压缩阈值 contextWindow − 16384、保留最近 20000 token；切点绝不落在 tool result 上；重复压缩会回退到上次保留边界，避免无声丢历史；长用户消息拆成两份摘要合并。切分支时还会自动生成分支摘要注入新路径——「试错换路线」不再等于丢掉全部上下文。

src/core/compaction/{compaction,branch-summarization}.ts

5. Codemode：把编排下沉到沙箱

模型写一段 JS，在 QuickJS(WASM) 里调用工具，中间结果完全不进上下文，只回传脚本输出。「列 200 个文件 → 过滤 → 只读 3 个」这类流程的 token 成本从 O(n) 降到 O(1)。更关键的是：codemode 自己就是一个普通扩展，只用了 exposure + prepareLoadout + ctx.executeTool() 三样公开 API，没有特权接口。

packages/codemode（QuickJS）· src/extensions/codemode/
顺带一提：上下文是它最在意的东西 技能（Skills）启动时只注入 name/description/path，全文按需加载；工具结果统一 2000 行 / 50KB 截断并告知模型完整输出在哪；模型目录只收录支持工具调用的模型；缓存命中/未命中可观测，还支持空闲期 prompt-cache 保温（cacheWarming: off|streaming|idle）。

06风险清单

风险真相程度怎么应对
没有内置沙箱 官方文档直说：工具使用 Pi 进程的 OS 权限，扩展与 Pi 同进程同权限；项目信任不是安全边界，它只管「要不要加载项目里的扩展」，不限制工具能碰什么 高容器 / VM / 专用低权限账户；凭据短期化；用 pi-env 只把工具隔离出去
实验包无兼容保证 protocol 自述 “no compatibility guarantees”，durable/server/client/env 同样标注 experimental 中高锁 tag；协议层加适配器，别让业务直接依赖
概念负载重 transcript 权威 + 分节 prompt + 暴露级别 + loadout + 投影/压缩 + 四种模式，理解成本不低 中从 SDK + 单个扩展切入，别一上手改内核
模型目录依赖外部数据源 目录由 models.dev / OpenRouter / AI Gateway 聚合生成，原始数据不入库（构建时 hydrate） 中build:offline；内网手工声明 modelOverrides 的窗口与缓存策略
会话明文 会话是明文 JSONL，可能含 prompt、命令输出、文件内容甚至泄露的凭据；/export、/share 会整包带走 中把会话目录当敏感数据管理；导出前审查
Bus factor 6,839 次提交中 57% 来自单一作者（Mario Zechner） 中低评估维护者结构与长期路线；关注企业/商业支持面

07选型建议

结论说明
适合 想做自己的编码/终端 Agent 产品；需要深度定制工具与上下文策略；有内网/合规要求要自托管 + 接私有模型；团队愿意花 1～2 周读源码
不适合 只想要开箱即用的 SaaS；需要内置多 Agent 编排图（Pi 有意不做）；需要厂商提供 SLA 与安全沙箱；不想碰 TypeScript

如果决定用，落地五步

  1. 先跑通再读源码：pi 交互模式 + /login，用真实任务感受工具集与会话行为。
  2. 从扩展起步，不动内核：先写一个只读工具（pi.registerTool() + readOnlyHint），再逐步接权限网关（tool_call 钩子 + ctx.ui.confirm）。
  3. 按部署形态定安全边界：容器化运行，挂载白名单目录，凭据最小化——不要指望 Pi 自己隔离。
  4. 上成本与缓存观测：开启 cacheWarming、关注 cacheRead 占比、用 /session 看分模型成本；大输出优先走 codemode 而不是灌进上下文。
  5. 锁版本 + 建回归集：锁定 tag，把实验包隔离，升级前跑自己的回归用例。
最容易踩的三个坑 ① 改了 agent.state.messages 却发现模型没变（权威在 SessionManager）。
② 注册了工具但模型看不见（非 direct/model-only 的暴露级别注册时不激活）。
③ 用 agent_end 判断「跑完了」（之后还可能有重试/压缩/队列续跑，应该用 agent_settled）。

速查：想做 X，用哪一层

需求入口
加模型可调用的能力 / / 命令 / 快捷键扩展：registerTool · registerCommand · registerShortcut
拦截工具调用、做审批与审计扩展事件：tool_call / tool_result / afterToolCall
