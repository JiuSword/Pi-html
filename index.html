00摘要 · 十条结论

如果只能带走十条判断，就是这十条。每条在后文都有源码或官方文档依据。

#结论为什么重要
1它是 harness（底座），不是框架全家桶官方明确「不做 sub-agents、不做 plan mode、不做内置沙箱」，把这些留给扩展与部署层。评估时要按「可改造的底座」而不是「开箱即用的平台」来打分
2依赖方向单向（实测无环）；但应说「四个依赖梯队」而非「四层」ai → agent → coding-agent 是一条主线；ai+chord → durable → env 是另一条互不依赖的主线。只取前两个包就能自建 Agent（agent 确实只依赖 ai）；但注意 durable 是第二套 agent 运行时，它不用 agent-core
3内核极小：循环 949 行，模型层 2.7 万行，应用层 8.6 万行复杂度集中在「工具怎么暴露、上下文怎么回收、能力怎么插进来」三个真问题，而非抽象层次
4Transcript 是唯一权威会话记录决定 system prompt、工具声明与模型上下文。这消灭了「UI 看到的 ≠ 模型看到的」这类最难查的 bug
5工具是 五级暴露模型direct / model-only / codemode / deferred / hidden：「模型看得到」≠「能调得动」。MCP 工具爆炸时这是决定 token 成本的关键设计
6Codemode 是差异化武器模型写 JS 在 QuickJS(WASM) 里调工具，中间结果不进上下文；且它自己只是普通扩展，无特权 API
7会话是可分支的 JSONL 树压缩与分支摘要都是「往树里追加条目」，原历史永不删除。这是生产级上下文管理的地基
8没有内置沙箱官方文档直说扩展与 Pi 同进程同权限、「项目信任不是安全边界」。安全责任落在部署层——这是选型时最大的决策点
9仓库本身是「Agent 优先」的工程样本AGENTS.md 禁止 git add -A / reset --hard / stash，因为多 Pi 会话可能并行改同一工作区。这套纪律可以直接搬走
10迭代极快，但作者高度集中14 个月 6,839 commits、302 个 tag、近 30 天 498 commits；同时 57% 提交来自单一作者，bus factor 需要纳入评估
给你的判断框架 需要可嵌入、可扩展、成本可控的编码/终端 Agent，且愿意读源码 → Pi 值得投入评估； 需要开箱即用、内置多 Agent 编排、厂级 SLA 与沙箱 → 它不是答案（有意不做）。这两句话贯穿全文。

01项目定位与全景

1.1 一句话定位

仓库 README 与官网（pi.dev）的自述高度一致：Pi is a minimal, extensible agent harness that you can make your own。官网 slogan 更直白：“There are many agent harnesses but this one is yours.”

它刻意做减法的三处「不做」，比它做了什么更能定义它：

  • 不做 sub-agent / plan mode —— README 原文：“ships with powerful defaults but skips features like sub-agents and plan mode”，需要什么就让 Pi 自己写扩展，或装一个 Pi package。
  • 不做内置沙箱 —— 把隔离责任交给容器/VM/专用账户（见第 11 章）。
  • 不做重编排 —— 内核保持极简，能力通过 extensions / skills / prompts / themes / packages 组合进来。

分发形态四种：交互式 TUI、print/JSON 批处理、RPC（跨语言）、TypeScript SDK（进程内嵌入）。四者共用同一套 agent 与 session 机制，这是它可以被嵌入的前提。

2.3 状态权威归属（理解 Pi 的关键）

为什么需要讨论「谁是权威」？因为 agent 应用里同一份「对话历史」几乎总会出现在两个地方：内存里的 agent 状态（给 UI 渲染、给扩展读）和持久化的会话记录（给下次启动恢复）。 一旦两者都能写，就会遇到经典的「双写不一致」：UI 里删了一条消息、或扩展往内存里插了一条，而落盘的是旧版本——下次打开会话，历史突然变回去了；更糟的是，模型这一轮看到的和下一轮看到的不是同一份上下文。

Pi 的做法是：树是事实，模型看到的是投影。会话文件里的条目是唯一事实，内存里的 agent 状态只是它的一个视图；每次请求前用 SessionManager 重新投影出上下文。

Pi 反复强调「每个状态只有一个权威来源」。这条原则解释了大量看似反直觉的 API 行为：

状态权威来源工程含义
模型上下文SessionManager 的活动分支 + compaction 投影直接给 session.agent.state.messages 赋值不会改变持久化上下文
System Prompt 与工具声明Transcript 中的 system 消息（首条为 prompt，后续为增量 patch）agent.state.systemPrompt 是只读的「重放」视图
可执行工具集（loadout）agent.state.tools每次请求前与 transcript 声明做 diff，不一致就注入一条 system 变更说明
会话历史JSONL 文件的 id/parentId 树分支永不删除，只移动叶子
项目资源信任决策后的 ResourceLoader拒绝信任即跳过受保护资源（但 sessionDir 查询无法撤销）
SDK 使用者最容易踩的坑 docs/sdk.md 原文：“SessionManager is authoritative for finalized model context. Assigning session.agent.state.messages does not replace persisted context.” 要注入历史，必须构造包含这些 entry 的 SessionManager；要替换上下文，用 prepareRequest。

27,242 行 / 199 个源文件 / 174 个测试文件。它是整个栈里最厚的基础设施，也是复用价值最高的包——即使你不用 Pi 的 Agent，也可以单独用它统一多厂商模型接入。

3.1 数据模型：所有 Provider 的公共语言

核心类型在 packages/ai/src/types.ts（893 行）。设计上有两处值得注意：不透明签名用于保留厂商私有的推理回放数据，以及 deferred（延迟响应）语义——这两点很多统一 LLM 层都没覆盖。

消息与内容块（简化）typescript
type Message = SystemMessage | UserMessage | AssistantMessage | ToolResultMessage;

interface TextContent     { type: "text"; text: string; textSignature?: string; }
interface ThinkingContent { type: "thinking"; thinking: string;
                              thinkingSignature?: string;   // 厂商私有不透明回放数据
                              redacted?: boolean; }              // 被安全过滤，密文保留以维持多轮连续
interface ToolCall        { type: "toolCall"; id: string; name: string;
                              arguments: JsonObject;
                              thoughtSignature?: string;         // Google：复用思考上下文
                              namespace?: string; }               // OpenAI Responses：动态加载工具的命名空间

interface Usage {                                        // 缓存与成本是一等公民
  input: number; output: number;
  cacheRead: number; cacheWrite: number; cacheWrite1h?: number;
  reasoning?: number;                    // output 的子集，仅部分厂商报告
  totalTokens: number;
  cost: { input; output; cacheRead; cacheWrite; total };
}

type StopReason = "pending" | "stop" | "length" | "toolUse" | "error" | "aborted" | "deferred";

ToolResultMessage 用条件类型强制 details 必须是 JSON 兼容结构，从类型层面保证「可持久化」；stopReason 里的 "deferred" 配合 DeferredHandle（含 expiresAt、pollAfterMs）支持批处理/异步模型响应。

3.4 鉴权链与推理等级

鉴权解析是一条链：Provider 自带的环境变量 → Pi 凭据存储（/login、pi auth）→ OAuth（订阅制、Vertex、Copilot）→ 运行时覆盖（--api-key 不落盘）→ 动态刷新钩子 getApiKey(provider)。同时支持注入 fetch 与请求头变换钩子。

7 档统一推理等级：off | minimal | low | medium | high | xhigh | max，跨厂商语义统一并按模型能力自动 clamp；token 型 Provider 可用 thinkingBudgets 自定义每档预算（默认 minimal 128 / low 512 / medium 1024 / high 2048），可用 samplingParamsByThinkingLevel 为不同档位设置不同采样参数。

成本核算：Usage.cost 分 input / output / cacheRead / cacheWrite 四项，Anthropic 的 1h 缓存写入单独可辨（cacheWrite1h）。Context 完全可序列化，因此支持跨厂商中途换模型（cross-provider handoff）而不破坏历史消息形状。

9tool_execution_update+ partialResult工具主动上报进度（工具调 onUpdate() 才会触发，不调就没有）

5.2 五级暴露模型（最具辨识度的设计）

先问：为什么不直接「所有工具都声明给模型」？

传统 agent 的做法是把所有工具的 schema 一股脑塞进 system prompt。工具少的时候没问题，工具一多就撞上四个具体问题：

问题现象Pi 的对策
提示词装不下挂 5 个 MCP server 就多出几十个工具，schema 挤占大量 token，且每轮都要重发codemode / deferred：工具不写进 prompt，只对脚本/搜索可见
有些工具不该被模型直接调编排型工具（如 codemode 本身）自己就是调度器，再让模型直接调它没意义model-only：声明给模型看，但永不被其它工具调用
工具太多选不准几十个工具同时出现，模型容易选错deferred + tool_search：按需搜索并激活
工具不能注销没提供 unregister，扩展重载后旧的会残留hidden：重新注册同名工具即可「撤回」

五级到底各是什么

底层是把传统的一维概念拆成两个维度：是否向模型声明（declared） 与 是否可被调用（callable）。

exposure向模型声明可被 executeTool() 调用codemode 列出典型用途
direct（默认）✅ 激活时✅ 激活时—常规工具
model-only✅ 激活时❌ 永不—编排型工具、向用户提问的工具
codemode❌（除显式激活）✅ 注册即可✅只希望被脚本调用的工具
deferred❌✅❌数量巨大的工具集，交给 tool_search 按需激活
hidden❌❌❌「撤回」工具（工具无法注销，只能隐藏）

配套三件事：激活集（loadout）——注册 direct/model-only 会立即激活，其余级别注册时不激活，需由 loader 工具调 setActiveTools() 选择性激活；namespace——把一组工具聚合（MCP server 天然如此），instructions 不参与列表展示、脚本用 describeNamespace() 读取；prepareLoadout(loadout)——可改写声明给模型的描述，并提交 hiddenDeclarations，即「仍是激活状态、仍可调用，但请求里不写它的声明」。

prepareLoadout 与 exposure 的分工

这两个东西容易混：exposure 决定「这个工具算什么」，prepareLoadout 决定「这次请求里它长什么样」。

exposure（注册时静态声明）prepareLoadout（每次计算 loadout 时动态返回）
回答的问题这个工具是否声明/可被调用？在本次请求里：声明写成什么、哪个声明暂时不写？
作用范围单个工具自己可以影响其它工具（包括自己）
返回值无（就是个字段）{ descriptions?, hiddenDeclarations? }
生效时机注册即定每次工具集变化时重算；只对处于激活状态的工具生效（源码 agent-session.js:1163 从激活集里取 hook）

典型用法：hiddenDeclarations 让一个工具「仍在激活集、仍可调用，但请求里不写它的声明」——这正是 codemode 把自己变成唯一入口的手段：其它工具仍能被脚本调用，但不占模型视野。

这四条已实测验证（不是文档复述） 写了一个真实扩展并跑通：① 注册时只有 direct/model-only 被激活，codemode/deferred/hidden 不激活； ② 可调用集 ⊋ 激活集（codemode/deferred 不被声明但可调用，hidden两者都不是）； ③ prepareLoadout 改写的 description 真的出现在发给 provider 的请求载荷里； ④ hiddenDeclarations 让工具从 system prompt 与 wire 载荷中消失，但它在激活集里依旧存在。详见 13.2 验证实验。

CompactionEntry（session-manager.ts）typescript
interface CompactionEntry<T = unknown> {
  type: "compaction"; id: string; parentId: string | null; timestamp: string;
  summary: string;              // 摘要正文
  firstKeptEntryId: string;     // 从这里开始保留原文
  tokensBefore: number;          // 重算后的压缩前 token 数
  usage?: Usage;                   // 摘要本身的用量也计入会话总计

四处值得注意的细节：

  • 切点规则：只能落在 user / assistant / bashExecution / custom 消息上，绝不切在 tool result（必须与它的 tool call 同生共死）。
  • 重复压缩：第二次从「上一次的 firstKeptEntryId」开始，而非从 compaction 条目本身开始，避免上一轮保留的原文被无声丢弃。
  • 长用户消息拆分：若单个 user 消息跨度本身超预算，切点落在跨度内部的 assistant 消息上，此时生成两份摘要再合并（历史摘要 + 跨度前缀摘要）。
  • 溢出恢复顺序：持久化最终响应 → 触发 turn_end/agent_end（扩展可见）→ 追加 context_edit 省略项 → session_before_compact 并落盘 compaction → 作为全新 run 重试；若恢复压缩失败或取消，则保留省略编辑、不追加 compaction、也不调度内部重试。

6.3 分支摘要与技能延迟加载

用 /tree 跳到另一分支时，Pi 找新旧位置的最近公共祖先，把离开路径上的条目按 token 预算摘要后，在导航点追加 BranchSummaryEntry，使「试错后换路线」不至于丢失全部上下文。摘要请求会关闭 prompt-cache 写入（一次性提示几乎不会被复用）。

07Codemode 与 MCP

7.1 Codemode 到底是什么

一句话：它不是让模型「多调用几次工具」，而是让模型「写一段程序去调用工具」。这段程序跑在沙箱里，程序内部的每一次工具调用与返回都不进入对话历史，只有程序最终输出/返回的内容回到模型。

一个类比 普通 tool calling 里，模型每做一步都必须把结果「念进会议纪要」——而纪要是永久的，每轮对话都要重读。 Codemode 相当于给模型一间带白板的小房间：它可以在里面反复翻资料、筛选、计算、并行调用，出来时只汇报结论。

模型实际看到的是什么

这个工具的入参只有一个字符串字段，不是参数化的 JSON schema（源码 coding-agent/src/extensions/codemode/tool.ts:90）：

codemode 工具的声明typescript
codemodeSchema = Type.Object({
  code: Type.String({ description: "Raw JavaScript source." }),
});

// 模型看到的 description 开头（原文）：
// Run JavaScript that calls other tools. The input is raw JavaScript (not JSON, no
// code fence), run as an async function body in a QuickJS sandbox: top-level `await`
// and `return` work. No Node, file system, network, or timers.

同一个任务，两种做法的差别

任务：在 300 个文件的仓库里找出所有 TODO 并按目录归类。

普通 tool callingCodemode

三个最容易误解的点

误解实际
「沙箱是安全边界」它是能力边界，不是安全边界。脚本里没有 Node、文件系统、网络、定时器，eval/Function 也只能在同一 VM 内产生更多代码，能力只有被注入的 tools.*。它不是「给模型一个 shell」，而是「给模型一张草稿纸，纸上唯一的权力是你本来就已经允许它调用的那些工具」。真正的安全边界仍在部署层（第 11 章）
「跑在沙箱里所以很安全/不产生副作用」工具真的会执行、副作用真的会发生。脚本崩溃前已完成的调用不会回滚（与数据库事务不同）；脚本结束时仍在运行的调用被取消，未 await 的 Promise 被丢弃
「中间结果不进上下文，稳赚」代价是中间过程对模型不可见。如果中间数据里有异常（某文件权限报错、返回格式不对），脚本没 text() 出来，模型就永远不知道。用它的前提是：你得替模型预先决定「什么值得看」。需要模型逐步观察中间结果再改变策略的任务，直接调工具反而更对

什么时候该用 / 不该用

场景推荐理由
多步 / 批量 / 需要过滤聚合用列目录→筛选→批量读这类流程，中间产物是纯浪费
需要并发用脚本里 Promise.allSettled 一次打多个工具，模型无法自己并发
工具数量巨大（多个 MCP server）用MCP 可声明 exposure: "codemode"，工具不写入 prompt，挂 3 个还是 30 个 server，系统提示词体积几乎不变
单步简单调用不用直接调更直接，写脚本反而多一层
需要逐步观察中间结果并改变策略不用中间过程对模型不可见（见上表第三行）
需要在中间插人工确认不用脚本是一口气跑完的，没有交互点

7.2 三种沙箱到底差在哪

先记住一句话：三者的 API、脚本环境、结果格式完全一致，差别只有一个——VM 跑在哪个线程 / 哪个隔离环境里。源码里说得很白：CodemodeSandboxBase 拿走工具表、默认值与在飞执行，子类只负责传一个 VmLauncher（“Subclasses only choose where the VM runs”）。

为什么「VM 在哪」会成为一个问题

因为 QuickJS 是同步执行的：脚本在计算的时候（而不是在 await 工具的时候）会一直占着线程。所以真正的问题不是「沙箱在哪」，而是这段同步计算会卡住谁。

沙箱VM 跑在哪卡住谁适用场景
CodemodeSandboxworker 线程（每次执行一个 VM）谁也不卡：宿主事件循环不受影响，且能直接 terminate() 硬停Node / Bun，应该首选。pi 自己用的就是这个
InlineCodemodeSandbox调用线程内卡住调用方自己（事件循环停摆）没有 worker thread、但能跑 WebAssembly 的运行时；且能接受阻塞
RemoteCodemodeSandbox另一个 isolate（通常是单独部署 Worker 里的 Durable Object）谁也不卡，但超时控制变弱（见下）线程必须保持响应的地方，如 Cloudflare 上服务一个会话的 DO
实测：worker 线程真的不会卡宿主 写了一个 800 万次循环、不调用任何工具、不 await 的 CPU 密集脚本，同时在宿主里挂一个 50ms 定时器： CodemodeSandbox 下定时器最大间隔仅 63ms（12 次采样）——若跑在调用线程里，这个间隔会接近脚本总执行时长。 同一套件还确认：while(true){} 死循环会被打断，报 Execution timed out after 200 ms，不会挂死。

Cloudflare 为什么必须用 Remote：一手数据

官方 README 给了 2026-10 的实测：把 QuickJS 放在会话的 Durable Object 内部，或放在该 DO 加载的 Dynamic Worker 里——一个计算 10 秒的脚本，会把该会话对象上所有其它请求延迟完整 10 秒。放到单独部署的 Worker 的 DO 里，延迟降到约 50ms。

因此 RemoteCodemodeSandbox 的设计是：工具与调用记录留在会话侧，只把 VM 送出去；每次工具调用再经 Workers RPC 回调到会话。绑定时要的是另一个 Worker 里的类（script_name），不能绑自己 Worker 里的类，否则阻塞又回来了。

超时语义三者不同（最容易踩） ① Inline / Remote 靠 interruptBudget（默认 100,000 次 QuickJS 中断回调预算）来打断「不 await 工具」的纯计算； ② 远程版有个重要差别（源码原话）：deadline 或 abort 之后，远端 VM 会继续计算，直到它下一次调用工具或耗尽中断预算——所以「超时」不等于「立刻停」； ③ 本地 worker 版才能硬停（用 Atomics 置中断位 + worker.terminate()）。
发布物的现实（避免踩坑） 1.1.0 的 npm 包里只有 CodemodeSandbox。文档说从 /portable 与 /cloudflare 导入 Inline / Remote，但我实测了发布物的导出面： package.json 的 exports 只有 . / ./declarations / ./source / ./worker，没有 portable 子路径；这两个类目前只存在于源码树的 src/portable.ts / src/cloudflare.ts。 要在 Cloudflare 上用，得从源码构建或等后续版本补齐。

另一个打包细节：打包后的 Node 程序里，worker 文件与 QuickJS 的 wasm 不在磁盘上，必须显式传 wasm: loadQuickJSWasm(path) 与 workerUrl。

模型写出的脚本（真实形态）javascript

7.3 MCP 集成：为什么自研一个客户端

先搞清楚「MCP 客户端」是什么

MCP（Model Context Protocol）本质是 JSON-RPC 2.0 之上的一个客户端–服务端协议。一个 MCP 客户端要干四件事：

#职责具体做什么
1传输stdio：把 server 当子进程启动，换行分隔的 JSON 走 stdin/stdout；Streamable HTTP：走 HTTP 流
2握手与版本协商发 initialize（带能力声明）→ 收 server 能力 → 发 notifications/initialized；版本不匹配报错
3调用与消息关联tools/list、tools/call、resources/list、resources/read…按 id 匹配响应，处理超时、取消、错误
4认证远程 server 的 OAuth：发现授权服务器元数据 → 动态注册客户端 → PKCE → 起本地回调端口收 code

「自研客户端」= Pi 把这四件事自己写了一遍：pi-mcp 共 18 个文件 / 3,244 行（client.ts 615 行 + Streamable HTTP 505 行 + OAuth 相关约 1,000 行）。

  2. 语义适配成本：Pi 要的是「MCP 工具 → AgentTool、结果 → pi-ai content blocks、OAuth 凭据 → Pi 凭据存储」；还要把工具名转成 Pi 的 identifier 规则、把 MCP 暴露级别映射进五级模型（源码里就一行 codemode → deferred）。包一层官方 SDK 反而更绕。

代价，以及 Pi 怎么兜底（最值得学的一部分）

代价是能力子集：如果你的 MCP server 依赖 prompts（斜杠命令式提示）、资源变更订阅、sampling（server 反向调模型）、elicitation（server 向用户提问），Pi 不支持。

8.1 JSONL 会话树

会话存储于 ~/.pi/agent/sessions/--<路径净化后>--/<时间戳>_<id>.jsonl。每条 entry 有 id / parentId 形成树，currentEntry 指向活动叶子；从更早的 entry 继续对话就是在同一文件里再开一条分支，fork/clone 则把选中历史复制进新文件。

8.2 Durable、远程执行与协议栈

pi-durable（2.2 万行，experimental）解决另一个场景：把 agent 做成可恢复的服务。核心承诺是「先提交、后展示」——对话、模型轮次、工具调用与你的状态先写入存储，再对外可见；进程中途死掉，重新打开存储就能接着跑。提供任务图与子任务、多会话与 fork、reset/handoff、hooks、用量与成本、以及可替换的 ExecutionEnv。

包职责与关键设计
pi-env让工具在另一台机器上跑：Rust daemon 经 SSH 部署（按 SHA-256 命名并在每次启动前校验）；ssh 使用 BatchMode、严格 host key（独立 known_hosts + 固定别名）、无任何端口转发；支持 Linux/macOS/Android(Termux)/Windows × x86-64/arm64
pi-protocol线上协议（experimental v8）：4 字节大端长度 + 定长 CBOR 项；路由信封 {serverId} 或 {serverId, sessionId, attachmentId}；载荷为不透明严格 JSON；默认限额 16 MiB/帧、1,000,000 元素、64 层嵌套；无兼容保证
pi-client传输无关客户端：先握手校验逻辑 serverId 与物理端点一致；不自动重连、不重放；订阅先收完整快照再 start() 释放缓冲更新
pi-server把连接路由到应用托管的 durable Session；一个会话可挂多个 presentation；重复 attach 幂等；断连后等已接受的调用结算完才释放 attachment；server 只校验路由、不解业务载荷
chord服务语义层：facets（可拆到不同进程/环境的插件片段）、singleton/keyed 服务、复制状态（原子 overlay 事务 + 不可变快照 + delta 编解码）。协议层只验证「是严格 JSON」，语义由 chord 在服务适配边界解析
pi-telemetry只提供契约：显式的 TelemetryContext/TelemetrySpan、NOOP 实现、内存参考实现 + 一致性测试；无 exporter、无全局 current-span 状态

- 禁用 any；只使用「可擦除 TS 语法」（不用 enum / namespace / 参数属性）

13.1 五条来自真实负载的结论

结论数据与含义
1. 缓存命中率决定成本量级99.29% 输入命中缓存，直接对应第 6 章的设计：分节 system prompt + 增量 patch（保证前缀稳定）、cacheWarming 保温、缓存命中可观测。前缀一旦被扰动缓存就全丢，所以这些设计不是可选项
2. 瓶颈是人，不是工具工具批 p50 仅 0.34 s、p90 4.92 s；而 3 次 ask_user 各等满 300 s 上限，合计 15 分钟——那不是机器耗时，而是人在阅读、判断与决策（选择方向、确认纠错意见）。3.94 h 墙钟中，真正的机器工作不到 15 分钟
3. 上下文线性增长，但压缩在本会话「根本没触发」上下文从 4,036 线性涨到峰值 246,225（净增 ≈1,485 token/次）。但 deepseek-flash 窗口是 1M，压缩阈值 ≈ 983.6K，还差 737K：会话里 0 条 compaction 记录。按同速外推，128K 窗口约第 74 次调用就会触发压缩，200K 约第 124 次，256K 约第 163 次——同一个任务，换个窗口小的模型，压缩必然发生；用 1M 窗口跑 182 次调用都碰不到。压缩是否需要，取决于「窗口 ÷ 任务长度」这个比值，而不是上下文绝对值
4. 工具失败是常态，恢复能力才是关键13 次失败（8.6%）覆盖 6 类原因：网络超时、GitHub HTTPS 不通、NVM 防火墙拦截、路径中文编码、edit 匹配不唯一、路径审批超时——没有任何一次中断整个任务。这就是「工具抛错 → isError 结果 → 模型换方案」回路的实际价值
5. 成本量级参考「完整源码调研 + 三层 HTML 报告 + 4 次 git 提交 + 1 次上游仓库完整克隆」全流程 $0.359；单次工具调用摊薄 $0.0024
本章数据的边界（勿当成基准） N=1：单模型、单任务类型、单机无并发，不反映吞吐或高并发表现；成本绝对值由 DeepSeek 的定价与缓存策略决定，换模型必须重新标定；延迟包含 pi-dashboard 与本地 Windows 环境的开销； 8.6% 的错误率来自一次「充满环境摩擦」的真实任务（网络受限、NVM 防火墙、路径审批），不代表稳态错误率。 它证明的是「Pi 能跑通真实端到端任务」，不是「Pi 的性能基准」。
更重要的是：哪些结论未被验证。本会话峰值仅占 1M 窗口的 24.6%，压缩与分支摘要全程未触发（0 条 compaction 条目）， 因此第 6 章的压缩阈值、「切点绝不落在 tool result」等规则只经过了源码与文档核对，没有获得实测验证；同理，扩展系统、codemode、MCP、RPC 模式于本次运行中均未使用。 读者可以据此判断：本章数据支撑的是「内核循环 + 工具执行 + 缓存 + 会话存储」这条主链，其余章节仍是代码阅读结论。
