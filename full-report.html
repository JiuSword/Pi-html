00TL;DR · 十条结论

如果你只有 3 分钟，读这一段。每条都可在后文找到源码依据。

01
它是「harness」，不是「框架全家桶」

自述为 minimal, extensible agent harness that you can make your own。刻意不做 sub-agents 与 plan mode，把这类能力留给扩展生态。

02
四层可独立取用

pi-ai（模型）→ pi-agent-core（循环）→ pi-coding-agent（应用）→ durable/server/protocol（分布式）。下层不强依赖上层，SDK 可按需取用。

03
1.8 万行内核 vs 8.6 万行应用

真正的 Agent 循环只有 949 行（agent-loop.ts），模型层 2.7 万行。复杂度集中在应用层的工具/会话/扩展/UI 装配。

04
Transcript 是唯一权威

会话记录决定 system prompt、工具声明与模型上下文；agent.state.messages = [...] 不会替换持久化上下文。这是避免「两份上下文」bug 的关键设计。

05
工具暴露分级（5 档）

direct / model-only / codemode / deferred / hidden。「模型看得到的工具」≠「能调用的工具」，用于 token 经济与编排。

06
Codemode 是它的差异化武器

模型写 JS 在 QuickJS(WASM) 沙箱跑，中间工具结果不进上下文，只回脚本输出。且它只是普通扩展，无特权 API。

07
会话是一棵可分支的树

JSONL + id/parentId，支持 fork/clone/import。压缩（compaction）与分支摘要都是往树里追加条目，原历史永不删除。

08
没有内置沙箱

安全模型是显式信任 + OS 权限 + 容器化。扩展与 Pi 同进程同权限；官方文档明确承认这一点，并把隔离责任交给部署方。

09
仓库本身是「Agent 优先」的

AGENTS.md 规定：禁止 git add -A/reset --hard/stash，因为多个 Pi 会话可能并行修改同一工作区。这是为 agent 协作而写的工程规范。

10
迭代极快，但核心作者集中

14 个月 6,839 commits、302 个 tag；近 30 天 498 commits。同时 57% 提交来自单一作者（Mario Zechner），bus factor 值得关注。

给你的一句话结论 如果你要做的是「可嵌入、可扩展、可远程、成本可控」的编码/终端 Agent，Pi 的分层、工具暴露模型与 codemode 设计值得直接借鉴甚至复用下层包； 如果你要的是开箱即用的多 Agent 编排平台，Pi 不是它——它把编排、子 Agent、沙箱都推给了扩展与部署层。

01项目定位与全景

1.1 一句话定位

仓库根 README 与 packages/coding-agent/README.md 自述：

原文Pi is a minimal, extensible agent harness that you can make your own. Adapt Pi to your workflows, not the other way around.

值得注意的「减法」设计：官方 README 明确写出 “ships with powerful defaults but skips features like sub-agents and plan mode”。也就是说：

Pi 的文档反复强调一件事：每个状态只有一个权威来源。这一点在 docs/sdk.md、packages/agent/README.md 中都有直白警告。

2.3 一次请求的完整路径

用户输入→ prompt template 展开 / @file 注入→ 消息写入树（父指针）→ 组装：system sections + 分支消息 + 工具声明→ prepareRequest（可替换上下文）→ provider 流式响应→ assistant 消息落盘→ 工具 preflight（tool_call 可否决）→ 并行/串行执行 + tool_result 可改写→ toolResult 消息落盘→ finishTurn 决策→ 下一轮 / agent_end → agent_before_settle → agent_settled
两个「边界事件」概念 agent_before_settle 是最后一个可动作的边界：它能追加条目并请求一次续跑；agent_settled 则是只读的终态通知，用于让外部集成确认 Pi 不会再自动继续。缺少这两个概念时，集成方很容易在「自动重试/压缩/队列」结束前误判会话已空闲。

03模型层 pi-ai

27,242 行 / 199 个源文件 / 174 个测试文件。它是整个栈里最「厚」的基础设施，也是复用价值最高的包。

3.1 数据模型

核心类型集中在 packages/ai/src/types.ts（893 行）。消息与内容块是所有 Provider 的公共语言：

消息与内容块（简化）typescript
type Message = SystemMessage | UserMessage | AssistantMessage | ToolResultMessage;

interface TextContent     { type: "text"; text: string; textSignature?: string; }
interface ThinkingContent { type: "thinking"; thinking: string; thinkingSignature?: string; redacted?: boolean; }
interface ImageContent    { type: "image"; data: string; mimeType: string; }
interface ToolCall        { type: "toolCall"; id: string; name: string; arguments: JsonObject;
                              thoughtSignature?: string; namespace?: string; }

interface Usage {                       // 成本与缓存感知是一等公民
  input: number; output: number;
  cacheRead: number; cacheWrite: number; cacheWrite1h?: number;
  reasoning?: number;                 // output 的子集，仅部分 Provider 报告
  totalTokens: number;
  cost: { input; output; cacheRead; cacheWrite; total };
}

type StopReason = "pending" | "stop" | "length" | "toolUse" | "error" | "aborted" | "deferred";

设计细节值得借鉴：

  • thinkingSignature / thoughtSignature / textSignature 保存 Provider 私有的不透明回放数据（如 Anthropic 加密推理块、Google thought context），使多轮推理连续性不被跨 Provider 抽象破坏；被安全过滤的推理内容以 redacted: true + 密文形式保留。
  • stopReason 里的 "deferred" 表示延迟响应（批处理/异步模式），配套 DeferredHandle（含 expiresAt、pollAfterMs）——这是很多统一 LLM 层没覆盖的场景。
  • ToolResultMessage 用条件类型强制 details 必须是 JSON 兼容结构，从类型层面保证可持久化。

3.2 流式事件协议

消费方式是一个 EventStream（可 for await），末尾用 await s.result() 取最终消息：

流式事件类型typescript
// 事件：start → (text|thinking|toolcall)_* → done | error
for await (const event of models.stream(model, context)) {
  switch (event.type) {
    case "text_delta":     process.stdout.write(event.delta); break;
    case "thinking_delta": /* 推理内容流式输出 */      break;
    case "toolcall_delta": /* 工具参数是「部分 JSON」，边流边解析 */ break;
    case "toolcall_end":   /* 参数已完整、可校验 */          break;
    case "done":           /* reason: stop | length | toolUse ... */ break;
    case "error":          /* event.error.errorMessage */       break;
  }
}
const finalMessage = await s.result();
context.messages.push(finalMessage);

两个易被忽略的能力：流式部分 JSON 工具参数（可在参数未完成时先做 UI 反馈）与 参数校验入口（validateToolArguments，与 TypeBox schema 联动，被 agent 循环复用做 preflight）。此外包内提供 faux Provider（24KB 代码）用于测试，无需真实 API。

3.4 鉴权与模型目录生成

鉴权解析链

  1. Provider 自带的工厂读取环境变量（如 OPENAI_API_KEY、ANTHROPIC_API_KEY）
  2. Pi 的凭据存储（/login、pi auth、SDK 的 readStoredCredential）
  3. OAuth 流程（订阅制 Provider、Vertex、Copilot、远程机器上的浏览器登录）
  4. 运行时覆盖：--api-key（不落盘）、getApiKey(provider) 动态刷新
  5. 可注入 fetch 与请求头变换钩子（before_provider_headers / before_provider_request 扩展事件）

模型目录（models.generated.ts）

  • 由 scripts/generate-models.ts 从 models.dev、OpenRouter 目录、AI Gateway 定价等外部源聚合生成
  • 原始数据目录 src/providers/data/ 被 .gitignore 排除 → 构建时才 hydrate（build:offline 保留离线路径）
  • .manifest.json 记录 generatedAt，可校验一致性
  • 仓库规则：禁止手改 models.generated.ts，必须改生成器再重生成
  • 另有独立 workflow publish-model-catalog.yml 与 update:model-catalog-pin 做目录发布与固定
内网/离线环境注意 模型元数据依赖外部数据源。内网部署要么走 build:offline（把 data 目录随包分发），要么在 modelOverrides 里手工声明目标模型的 inputLimits 与 promptCache，否则上下文窗口与缓存策略会失准。

3.5 推理等级、采样与成本

  • 7 档统一推理等级：off | minimal | low | medium | high | xhigh | max（THINKING_LEVELS / MODEL_THINKING_LEVELS）。跨 Provider 语义统一，并按模型能力自动 clamp；token 型 Provider 可用 thinkingBudgets 自定义每档预算（默认 minimal 128 / low 512 / medium 1024 / high 2048）。
  • 难度→参数映射：SamplingParamsByThinkingLevel 允许为每个等级声明不同的温度等采样参数。
  • 成本核算：Usage.cost 覆盖 input/output/cacheRead/cacheWrite 四项，Anthropic 的 1h 缓存写入单独可辨（cacheWrite1h）。会话级累计由 coding-agent 的 usage-totals.ts 汇总。
  • 跨 Provider 交接：Context 可序列化，因此可以在会话中途换模型甚至换厂商，历史消息保持同一形状（Pi 文档称之为 cross-provider handoff）。

4.3 Turn 生命周期与三个钩子

每轮 Provider 请求的生命周期text
选定输入（tool results / steering / follow-up）
  → prepareRequest      // 每次请求前重建权威上下文（含第一次）
  → provider response
  → tool results
  → finishTurn          // 决定 continue / end
  → turn_end
  → 现有续跑调度 或 agent_end
  • prepareRequest：在每次会话请求前安装「规范化持久化上下文」。典型用途是把 SessionManager 里加载的权威消息覆盖回请求上下文，避免扩展或 UI 造成的漂移。注意：它不会轮询队列。
  • finishTurn：取代了旧的 shouldStopAfterTurn。返回 {action:"end"} 会在 turn_end 后立刻结束本轮，且不再轮询队列；返回 {action:"continue"} 保证再发一次请求（若无工具结果/队列已满足，则会发一次「纯上下文」请求）。

4.4 工具执行、批处理与终止语义

并行 vs 串行

  • 默认 parallel：preflight 顺序执行（参数校验、beforeToolCall），允许的工具并发执行，tool_execution_end 按完成顺序发出，但落盘的 toolResult 消息与 turn_end.toolResults 仍按 assistant 源码顺序
  • sequential：逐条执行（历史行为）
  • 粒度：全局 toolExecution，或单工具 executionMode。任一工具声明 sequential，整批转串行

终止（terminate）语义

  • 三个来源可返回 terminate: true：工具 execute()、被阻止的 beforeToolCall、afterToolCall 覆盖
  • 效果：跳过该批之后自动的后续 LLM 调用
  • 约束：只有当该批所有已定稿的 tool result 都为 terminate 时才生效；混合批次照常继续
  • 该提示是运行时语义，落盘的 toolResult 仍是标准 LLM 工具结果
顺序保证 使用 Agent 类时，assistant 的 message_end 处理被当作屏障（barrier），因此 beforeToolCall 看到的 agent 状态里已经包含「发起该工具调用的那条 assistant 消息」。但如果你直接用低层 agentLoop()，事件流是纯观测性的——它保序但不等你的异步处理完成。

6.1 分节式 System Prompt

Pi 的 system prompt 不是一坨字符串，而是一组带名字的 section（preamble 无标签，其余包成同名标签）。这些 section 被写入 transcript 的 system 消息里，因此模型「看得见结构」，后续变更可以只发增量补丁。

Prompt 装配与增量 difftypescript

buildSystemPromptState(input)     // → { content, sections }：有 sections 时 content 为空

可注入面（BuildSystemPromptOptions）：自定义 prompt、selectedTools / hiddenTools、每工具的一句话摘要（toolSnippets）与规则条目（toolGuidelines）、附加规则（promptGuidelines）、appendSystemPrompt、任意 sections、工作目录、项目上下文文件、技能列表。

默认规则的生成是有条件逻辑的（buildRules）：例如「当启用了 bash/powershell 但没有 grep/find/ls 时」，才追加「用 shell 做文件操作」的提示；规则会去重，末尾固定追加 Be concise in your responses 与 Show file paths clearly when working with files。

项目上下文文件（AGENTS.md / AGENTS.override.md / CLAUDE.md 等）会被包成 <project_instructions path="..."> 注入——并且不受项目信任门控影响（官方明确提醒：把文件夹里的指令当不可信输入）。

中途改 prompt 的两种方式

  • 结构化：before_agent_start 事件提供 systemPromptOptions，优先改 section / 工具集 / 指引，让 Pi 追加 transcript 增量
  • 整体替换：返回 systemPrompt 或设置 forceSystemPrompt，Provider 会收到强制文本作为首条 system 消息（代价：丢失结构化记录）

技能是「延迟加载」的

启动时只把每个技能的 name / description / path 注入 prompt；任务命中后模型再自行读 SKILL.md 全文。这样既能让模型知道「有这个能力」，又不牺牲 token 预算。

6.2 压缩（Compaction）：生产级上下文回收

16384reserveTokens 默认
留给模型回答
20000keepRecentTokens 默认
保留最近多少个 token 的原文
2摘要机制
压缩 + 分支摘要

触发条件：contextTokens > contextWindow - reserveTokens。检查点有三处：多轮运行中「工具结果写盘后、下一轮 assistant 之前」（prepareNextTurn）、新用户输入之前、以及低层 run 结束后的「溢出兜底恢复」。手动触发为 /compact [instructions]。

算法步骤：

  1. 从最终投影（projection）向后走，累计 token 估算直到超过 keepRecentTokens，定位切点
  2. 收集「上一次保留边界（或会话起点）→ 切点」之间的消息
  3. 调用 LLM 生成结构化摘要（有上一份摘要时作为迭代上下文传入）
  4. 追加 CompactionEntry，记录 summary 与 firstKeptEntryId
  5. 重建上下文 = 摘要 + firstKeptEntryId 起的消息
CompactionEntry 结构（session-manager.ts）typescript
interface CompactionEntry<T = unknown> {
  type: "compaction"; id: string; parentId: string | null; timestamp: string;
  summary: string;              // 摘要正文
  firstKeptEntryId: string;     // 从这里开始保留原文
  tokensBefore: number;          // 重算后的压缩前 token 数
  usage?: Usage;                  // 摘要本身的 LLM 用量也计入会话总计
  details?: T;                    // 默认实现记录 readFiles / modifiedFiles
}

值得注意的细节：

  • 切点规则：只能落在 user / assistant / bashExecution / custom 消息上，绝不切在 tool result（必须与它的 tool call 同生共死）。
  • 重复压缩：第二次压缩从「上一次的 firstKeptEntryId」开始，而不是从 compaction 条目本身开始——这样上一轮被保留的原文仍会被纳入下一次摘要，不会被无声丢弃。
  • 切分长用户消息：若单个 user 消息跨度本身就超过预算，切点会落在该跨度内部的 assistant 消息上，此时生成两份摘要再合并（历史摘要 + 跨度前缀摘要），并标记 isSplitTurn = true。
  • 溢出/长度恢复顺序：先持久化最终 assistant 响应 → 触发 turn_end / agent_end（扩展可见）→ 为被放弃的尝试追加 context_edit 省略项 → 执行 session_before_compact 并落盘 compaction → 作为全新 run 重试。若恢复压缩失败或被取消，保留省略编辑、不追加 compaction、也不调度内部重试。
  • 原始历史永远保留：被压缩掉的条目仍在文件中，导出、计费、历史检索类扩展依然能查到被省略的尝试。

6.3 分支摘要（Branch Summarization）

用 /tree 跳到另一条分支时，Pi 会提议把「即将离开的工作」摘要后注入新分支：找新旧位置的最近公共祖先 → 收集离开路径上的条目 → 按 token 预算（新的优先）生成摘要 → 在导航点追加 BranchSummaryEntry。与压缩共享同一套结构化格式与累积文件操作追踪。

为什么这很重要 「分支」在多数 agent 实现里等于「丢掉一半工作」。Pi 用一次摘要把左侧历史压成一条条目注入右侧，使「试错后换路线」不至于让模型丧失全部上下文。另外它明确关闭摘要请求的 prompt-cache 写入，因为这种一次性提示几乎不会被复用。

  • 上下文窗口与压缩阈值都按「实际作答的物理模型」计算

沙箱内没有 Node API、文件系统、网络、定时器；脚本体是 async 函数体，支持顶层 await 与 return。

边界与限额

  • 首行可写 // @options: {"max_output_tokens":2000,"timeout_ms":60000}
  • max_output_tokens 默认 10000；超长输出保留首尾，完整文本写入临时文件并在结果里给出路径
  • 硬上限：文本 + base64 图像合计 16,777,216 字符，或 text()/image()/console 调用合计 100000 次即失败
  • timeout_ms 默认不设（图像生成可能耗时数分钟，别设太短）
  • 工具调用是真执行：失败前的调用不会回滚；脚本结束时仍在运行的调用被取消，未 await 的 Promise 被丢弃
  • store：单值 ≤ 262,144 字符，总量 ≤ 1,048,576；仅脚本成功时保留，落为会话中的 codemode-store 自定义条目（按分支可见）

工具调用的返回值形态：声明了 outputSchema 的工具返回结构化值。以 bash 为例，脚本拿到的是 { output, truncated, full_output_path?, exit_code, wall_time_seconds }（即使退出码非零）——output 上限 1 MiB，超长时保留首尾各 512 KiB 并在中间插省略标记。未声明 schema 的工具返回文本内容。

与模型可见性的配合：codemode.mode = on（默认）时其它工具仍被声明，只在描述里说明「如何从脚本调用」；only 时它们对模型隐藏，只能经脚本调用。codemode 描述里的工具声明共享 3000 估算 token 的预算（codemode.inlineBudget），因此 deferred 工具不列出——这也是「MCP server 连接前后描述保持一致」的原因。

为什么这是「省钱 + 变强」双赢 传统 agent 里，一次「列出 200 个文件 → 过滤 → 读 3 个」的流程会把 200 行输出全塞进上下文。codemode 让这段逻辑跑在沙箱里，模型只看到脚本的最终输出。并且它同时提升能力上限：脚本能并行调用（Promise.allSettled）、能组合工具能力，而模型不必「记住」中间态。

9.2 Durable：崩溃安全的嵌入式 Harness

pi-durable（22,473 行，标注 experimental）解决的是另一个场景：把 agent 做成可恢复的服务。核心承诺是「先提交、后展示」——对话、模型轮次、工具调用和你自己的状态都先写入存储，再对外可见；进程中途死掉，重新打开存储就能接着跑。

关键概念

  • Harness.open(storage, services, context) → root() 生根会话
  • 任务图与子任务（child tasks）、多会话与 fork、reset/handoff
  • 按会话的 agent、可重载（reload）、hooks
  • ExecutionEnv 抽象：本地 Node / 远程 RemoteExecutionEnv 语义一致（有 conformance 测试套件）
  • 存储抽象（MemoryStorage 等），并发/忙碌会话处理、用量与成本
  • 基于 chord 的文档状态与 delta 复制，为「同一会话多方观察」做准备

什么时候值得用它

需要「agent 作为长时任务服务」时：Worker/Serverless 场景、需要进程重启后继续、需要多个前端同时观察同一会话。若只是本地 CLI 或进程内一次性调用，用 pi-coding-agent 的 SDK 更简单——额外的持久化层是有成本的（状态机、调度、并发语义都要理解）。

11.1 为「多 Agent 并行」写的 Git 纪律

AGENTS.md 原文要点Multiple pi sessions may be running in this cwd at the same time, each modifying different files. Git operations that touch unstaged, staged, or untracked files outside your own changes will stomp on other sessions' work.
  • 禁止：git add -A / git add .、git reset --hard、git checkout .、git clean -fd、git stash、git commit --no-verify、force push
  • 提交要求：只 git add <明确路径>；提交前先 git status 自查；信息格式 {feat,fix,docs}[(ai,tui,agent,coding-agent)]: <message>
  • 冲突处理：只解决自己改过的文件的冲突；冲突出现在未改动的文件 → 中止并询问用户
  • 模型目录例外：models.generated.ts 允许随时一并提交（因为是生成物）

13.2 Recipe 1：带结构化输出的工具扩展

~/.pi/agent/extensions/ticket.tstypescript
import type { ExtensionAPI } from "@earendil-works/pi-coding-agent";
import { Type } from "typebox";

export default function (pi: ExtensionAPI) {
  pi.registerTool({
    name: "list_tickets",
    label: "List tickets",
    description: "List open tickets from the internal tracker. Use when the user mentions a ticket id or asks about open work.",
    parameters: Type.Object({
      status: Type.Optional(Type.Union([Type.Literal("open"), Type.Literal("closed")])),
      limit:  Type.Optional(Type.Number({ default: 20 })),
    }),
    // 声明了 outputSchema，codemode 脚本就能拿到结构化值
    outputSchema: Type.Array(Type.Object({ id: Type.String(), title: Type.String() })),
    annotations: { readOnlyHint: true },
    async execute(_id, params, signal) {
      const rows = await fetchTickets(params, signal);   // 失败就 throw，不要返回错误文本
      return {
        content: [{ type: "text", text: rows.map(r => `${r.id} ${r.title}`).join("\n") }],
        structuredContent: rows,
        details: { count: rows.length },   // 跟活动分支走的状态放这里
      };
    },
  });
}

要点回颖：description 要写清「做什么 + 什么时候用」（它直接决定模型何时选这个工具）；带 schema 的工具脚本可拿结构化值；只读工具声明 readOnlyHint 以免被审批网关拦截。

13.7 常见坑汇总

坑真相
“我改了 agent.state.messages 但模型没变”SessionManager 才权威；要改上下文得注入 entry 或用 prepareRequest
“工具为什么没被模型看到”检查 exposure 与 激活集：非 direct/model-only 注册时不会激活
“工具删不掉”工具无法注销，只能用 exposure: "hidden" 重新注册以撤回

“自定义消息被发送到模型了”convertToLlm 里忘了过滤自定义角色

五条来自真实负载的结论

  1. 缓存命中率决定成本量级：反推单价为新输入 $0.30/1M、缓存读取 $0.006/1M（约 50× 价差）。本会话输入侧共 18.52M token，99.29% 走缓存，把输入侧成本从约 $5.55 压到 $0.150（37×），总成本从约 $5.76 降到 $0.359。这正是第 6 章「分节 prompt + 增量 patch + 缓存保温」的真实收益——前缀一旦被扰动，缓存全丢。
  2. 瓶颈是人，不是工具：工具批 p50 仅 0.34 s、p90 4.92 s；而 3 次 ask_user 各等满 300 s 上限，合计 15 分钟人类思考时间。3.94 h 墙钟中真正机器工作不到 15 分钟。
  3. 上下文线性增长，但压缩在本会话「根本没触发」：上下文从 4,036 线性涨到峰值 246,225（净增 ≈1,485 token/次）。但 deepseek-flash 窗口是 1M，压缩阈值 ≈ 983.6K，还差 737K，会话里 0 条 compaction 记录。按同速外推：128K 窗口约第 74 次调用就会触发压缩，200K 约第 124 次，256K 约第 163 次——同一个任务换个窗口小的模型，压缩必然发生。压缩是否需要，取决于「窗口 ÷ 任务长度」，而不是上下文绝对值。这也意味着第 6 章的压缩与切点规则在本次运行中未获得实测验证。
  4. 工具失败是常态，恢复能力才是关键：13 次失败（8.6%）覆盖 6 类原因——网络超时、GitHub HTTPS 不通、NVM 防火墙拦截、路径中文编码、edit 匹配不唯一、路径审批超时——没有一次中断整个任务。这就是「工具抛错 → isError 结果 → 模型换方案」回路的实际价值。
  5. 成本量级参考：「完整源码调研 + 三层 HTML 报告 + 4 次 git 提交 + 1 次上游仓库完整克隆」全流程 $0.359。
